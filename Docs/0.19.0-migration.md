# 0.19.0 migration notes

0.19 changes how ReactiveDomain is packaged, and makes the behavioral changes listed in their own
sections below. No namespace or type renames, and a stream written by an earlier version replays
unaltered. The packaging changes are which package a consumer references and how the command-line
PolicyTool is installed.

Each assembly is its own package. `ReactiveDomain` delivers the CQRS-ES core — Foundation, and
through it Messaging, Persistence and Core — so a consumer referencing it keeps every assembly it
had, with two exceptions below.

## `TcpBus` needs its own package reference

Nothing in the core libraries depends on TCP transport, so it is now a separate package that is no longer included in `ReactiveDomain`.

A consumer that never touches TCP transport stops carrying a socket stack it was not using.

**What to do.** If you use `TcpBus`, `TcpBusClientSide` or `TcpBusServerSide`, add one reference:

```xml
<PackageReference Include="ReactiveDomain.Transport" Version="0.19.0" />
```

Namespaces and type names are unchanged, so that reference is the whole fix. Without it the build
fails on the transport types and nothing else.

## `ReactiveDomain.Policy` is now `ReactiveDomain.Policy.Core`

The `ReactiveDomain.Policy` **package** bundles both identity and policy, and keeps
delivering the same three assemblies. The assembly that used to share that name — the one holding
`Policy`, `Role`, `Permission` and `PolicyDispatcher` — is now `ReactiveDomain.Policy.Core.dll`.

Namespaces are unchanged, so existing projects will compile without changes, and streams written before this still replay.

**What to do.** Nothing, unless your code references the assembly rather than the namespace, e.g., an
`Assembly.Load`, a binding entry, or a build step copying `ReactiveDomain.Policy.dll` by name.

## PolicyTool installs as a .NET tool

`PolicyTool.exe` is a `dotnet tool` rather than a file copied into the output of any project that
references the Policy package.

**What to do.** Install it and call it by command name:

```
dotnet tool install --global ReactiveDomain.PolicyTool
policytool …
```

It is framework-dependent and needs a .NET runtime on the machine, whereas previously it was a
self-contained `win-x64` executable. A script invoking `PolicyTool.exe` out of a build output
directory should now call `policytool` instead.

## Commands can be awaited, and a nested send runs inline

`ICommandPublisher` gains `SendAsync`: send a command and await its response instead of blocking a
thread. It is a default interface member, so an implementation outside this repo keeps compiling; it
never throws for a failed command — the task completes with the same `Fail` that `TrySend` returns.

**Behavior change.** A command sent with `Send`, `TrySend` or `SendAsync` from inside a handler
running on one of a publisher's own queue threads now runs inline on that thread. Previously it was
enqueued; with one publish queue it landed behind its blocked sender and always timed out. Two
consequences for existing consumers:

- **Ordering.** The nested command's handler runs immediately — before events the sender published
  earlier in the same handler are themselves handled. A read model or saga relying on strict
  publish-then-send ordering across a nested send sees the new order.
- **Unchanged paths.** `TrySendAsync` still enqueues and returns, so fire-and-forget sends keep their
  timing, and a queue-affine command (`IQueueAffineMessage`) always goes to its own queue — which
  means a *blocking* nested send of one can still wait behind its sender and time out; affinity is
  preserved over liveness.

## `TryGetById` returns false only for "not found or deleted"

`IRepository.TryGetById` and `ICorrelatedRepository.TryGetById` caught every exception and returned
false, so a store outage or an event that no longer deserializes read as "does not exist" — and the
common try-then-create pattern then manufactured a new aggregate over an existing stream, surfacing
as a misleading `WrongExpectedVersionException` at save.

False now means exactly `AggregateNotFoundException` or `AggregateDeletedException`: there is no
usable aggregate at that id. Every other failure propagates.

**What to do.** Nothing, unless a caller relied on `TryGetById` returning false during transient
store failures; that caller now sees the failure itself and should catch it where it can be handled
honestly.

## Building a package locally

`dotnet pack src/ReactiveDomain.sln -c Release` writes every package to `packages/`, and `-c Debug`
does the same for a debug build. The version comes from the nearest `v` tag, so a working tree
between tags packs as a prerelease ahead of it; pass `-p:MinVerVersionOverride=…` to stamp a
specific one for a local feed.
