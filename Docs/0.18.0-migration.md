# 0.18.0 migration notes

A handful of 0.18 changes alter behavior consumers may be relying on without knowing it.
Everything else in 0.18 is additive.

## Unknown event types throw instead of becoming a silent `JObject` (#245)

Through 0.17, `JsonMessageSerializer` returned an empty `JObject` when the CLR type in the
event metadata could not be resolved. Listeners then skipped it. A renamed type, a missing
assembly, or a typo in the header looked like a healthy subscription that had simply never
seen that event.

In 0.18 the serializer throws `InvalidOperationException` unless you opt back into the silent
path:

```csharp
new JsonMessageSerializer(new JsonMessageSerializerSettings(throwOnTypeNotFound: false));
// or, after construction:
serializer.ThrowOnTypeNotFound = false;
```

A live listener and a catch-up <c>Read</c> still skip a poison event (log, advance the
checkpoint, continue) so a bad payload cannot stall a start or loop a reconnect. The throw is
for an explicit deserialize — a repository load, a read-model inject, a test.

## `ReadModelBase.Version` does not count the live transition (#211)

`CatchupSubscriptionBecameLive` is still dispatched to handlers. It is not a stream event, and
it is no longer included in `Version`. A model that read ten events and went live has
`Version == 10`, not 11. Tests that asserted an exact `Version` after `Start` should drop the
off-by-one, or keep using `AssertEx.AtLeastModelVersion`.

## A resume that finds nothing new keeps its checkpoint (#162)

`IStreamReader.Position` / `Checkpoint` after a `Read` that found nothing newer are the
checkpoint the read was asked to resume after — not null. Null remains only before the first
`Read`, or after a `Read` of a stream that does not exist. A listener attached from that
reader therefore continues from where history left off, rather than from the beginning of the
stream.

## Public `Handle(T)` on a read model (#RD0001)

`ReadModelBase.Handle(IMessage)` enqueues. A public `Handle(T)` for a type the model
implements `IHandle<T>` for is a better overload, so `model.Handle(evt)` runs the handler on
the calling thread and skips the queue.

Implement the interface explicitly:

```csharp
void IHandle<OrderPlaced>.Handle(OrderPlaced @event) { /* fold */ }
```

`ReadModelBase.Handle(IMessage)` enqueues onto the model's queue thread. A public
`Handle(OrderPlaced)` is a better overload, so `model.Handle(evt)` binds to it, runs the
handler on the calling thread, skips the queue and races every other fold. The analyzer
**RD0001**, shipped in the `ReactiveDomain.Foundation` package, warns on that shape.

Two paths inject a message from outside the model's own listeners, and both remain open:

- `Publish` (or the `IMessage` `Handle` on the base) enqueues it, so it folds on the queue with
  everything else. Prefer this outside tests.
- `DirectApply` applies it on the calling thread, under `ReaderLock`, bypassing the queue.
  `ReactiveDomain.Testing`'s `UpdateFromAggregate` is built on it, which is what makes it
  useful in unit tests.

What the analyzer refuses is neither of those — it is the *typed* public `Handle(T)`, which a
caller reaches by accident.

## A read model refuses a stream it is already listening to (#296)

Through 0.17, starting the same stream twice on one read model was permitted and produced two
listeners on it. Both feed the model's single queue, and the model has one set of handlers, so
every event on that stream is handled twice with nothing able to tell the two deliveries apart.
A handler that recomputes absorbs it; one that accumulates — a running total, a count, an
appended list — is wrong from the second delivery onward. `GetCheckpoint()` also reports the
stream twice, which breaks any caller treating the result as keyed by stream name.

In 0.18 the second start throws `InvalidOperationException`:

```
SchedulesRm is already listening to '$ce-Schedule'. A second listener would hand this model
every event on that stream twice.
```

This applies to every `Start` and `StartAsync` overload, and across them: the category overload
and the named overload refuse each other when the name they resolve to is the same.

**What to do.** The throw names the stream. Either the second start is redundant — delete it —
or the two starts were meant for different streams and one is wrong. Where a model genuinely
needs an event twice, handle it once and fold it twice; there is no supported way to deliver it
twice.

**What still gets through.** The rule is one *listener* per stream, not one delivery per event.
A category stream and a member aggregate's own stream are different names carrying overlapping
events, and so are two categories whose membership overlaps. Either pair still delivers an event
twice and neither is refused.

**Restarting is unaffected.** Disposal releases the name, so a stream can be started again after
its listener drops.

## A typed stream resumed at its last event redelivers nothing (#296)

Through 0.17, the typed overloads — `Start<TAggregate>(id, checkpoint: …)`,
`StartAsync<TAggregate>(id, checkpoint: …)` and the category forms — resumed from the
*beginning* of the stream when the checkpoint found no newer events: every event the model had
already folded arrived again, live. The named overload, `Start(string stream, checkpoint: …)`,
held the checkpoint. A model restored from a snapshot and started with the checkpoint it saved
was therefore correct on a busy stream and wrong on a quiet one.

In 0.18 every overload holds the checkpoint. A stream with nothing after it delivers nothing, and
the listener attaches at the checkpoint, not at the start.

**What to do.** Nothing, unless a handler was written to absorb the redelivery — a recompute that
tolerated seeing its history twice. That tolerance is no longer exercised on this path, but it
was never wrong, and it still matters for the overlapping-stream deliveries described above.
